# 配置回退与恢复边界

配置回退统一使用 `scripts/manage/manage.ps1`。旧 baseline 与 Provider 入口已从正式源码树移除；日常操作见[项目 README](../README.md)，开发与清理约定见[文档导航](README.md)。

## 日常回退

```powershell
# 列出完整版本和旧备份；不激活任何配置
.\scripts\manage\manage.ps1 -Action history

# 或使用菜单 5，按编号或完整 build_id 选择
.\scripts\manage\manage.ps1 -Action rollback -BuildId 版本ID

# 完整检查（会先尝试恢复待完成同步，可能写文件）
.\scripts\manage\manage.ps1 -Action check
```

只接受受限 ID，不接受任意绝对路径、`..` 或重解析点。恢复会核对历史版本的完整文件集合、摘要、两端标记、核心版本与核心 SHA-256，再复制到新的 release 并重新运行两端核心检查。全部成功后切换活动指针；源版本不改动，同一版本可恢复多次。

含 `rule-set-snapshot` 的新版本同时恢复规则原始 SRS、解析结果及元数据，使用历史内嵌内容，不重新下载今天的规则替换它。完整文件、核心身份和配置内嵌内容必须对应。旧格式版本按原有检查恢复，原配置中的远程规则依赖也会保留；它们不能为新策略提供完整的离线规则快照，迁移后先执行一次成功的在线更新。

`runtime/active-release.json` 是唯一正式状态。历史版本不会自动删除；首次成功更新会把原有有效静态 dist 保存为 `legacy-dist-import` 版本，供后续恢复。不要手改 release 文件或指针，也不要把候选目录命名成“已验证”来绕过检查。

回退**不恢复**源码、`config/` 工作策略/清单、上游订阅、客户端选择或系统网络。恢复后 `check` 如果提示工作配置与版本输入不同，是正常的边界提示：下一次更新会使用当前工作配置，而非回退版的输入快照。如要继续在旧策略上开发，先对照 release 的 `inputs/config/` 手动审阅差异，不盲目覆盖本机文件。

## 中断与磁盘错误

激活前失败：旧活动配置与其缓存继续有效；未完成候选保留供诊断，不列为有效版本。

激活后导出或工作清单同步失败：控制台明确显示已提交但同步未完成，并非全部失败回滚；保留 `runtime/projection-journal.json`，CLI 退出码为 `10`。发布器继续从完整活动 release 服务，两端导入 `dist` 前执行：

```powershell
.\scripts\manage\manage.ps1 -Action recover
.\scripts\manage\manage.ps1 -Action check
```

`status/history/sources/explain/lint/doctor` 只读查询不会恢复事务；下一次构建、维护、回退或完整检查会先尝试恢复。若工作文件在中断期间被外部改动，恢复拒绝覆盖，请先保存该文件并对照 journal 与活动版本输入处理冲突。不要删除 journal 来“清理干净”。

维护操作以实际捕获的清单和输入摘要作为冲突基准。既有输入被修改或删除时，提交前会拒绝激活，提交后会拒绝继续同步并保留 journal；不会自动恢复被删除的既有输入。只有新 journal 明确记录为本次新增的输入才允许创建，已创建且摘要匹配的新增输入可以复用。旧 journal 缺少该记录时，缺失输入需要保存证据并人工审阅，不能假定它是待补建文件。

摘要检查属于乐观并发控制，外部编辑器不持有项目锁。维护或恢复期间避免同时保存相关文件；新增输入发生部分写入时也会作为冲突保留，不自动覆盖。

`recover` 也可重新导出活动版本，修复没有 journal 的 dist 手工改动；它不改变活动版本，不修复损坏的 release，不重置客户端数据库。

## 旧快照导入

旧 `runtime/backups/<名称>` 只支持读取诊断和受限恢复：

```powershell
.\scripts\manage\manage.ps1 -Action rollback -Legacy -BuildId 20261024-快照名称
```

要求两端 JSON/验证标记匹配、验证核心版本正确，再通过当前固定核心检查。缺标记、坏摘要、Provider 动态依赖快照默认拒绝。旧快照不能补造“曾经验证”的证据；成功恢复写入新 release，不修改历史文件。旧格式没有完整输入/缓存证据：导入版使用当前工作输入作为旁证，缓存为空，不代表重建了历史订阅状态，之后离线更新可能无可用缓存。

有坏摘要或缺少标记的旧快照不能直接恢复。私有审计、baseline 或源码快照不是日常 release，不接受任意路径参数绕过检查。

## 四类恢复分别处理

| 范围 | 必须保存什么 | 本流程不能保证什么 |
| --- | --- | --- |
| 发布配置 | 同一 release 的两端 JSON、标记、输入与缓存 | 自动恢复源码或客户端当前选择 |
| 源码与策略 | 完整工作区、暂存区、未跟踪文件与明确基准 | 等于 Git HEAD 或历史满意版本 |
| 订阅输入 | 私密清单、静态节点、对应版本缓存 | 上游此刻仍提供同样节点；远程规则集内容不变 |
| 客户端选择/缓存 | 各设备 profile、缓存与选择记录 | 另一台设备状态也同步恢复 |

Git 提交记录描述源码状态，不代表某台客户端正在使用的配置。恢复源码时先检查提交差异；不要使用 reset/clean 或删除 cache.db 代替选择正确的配置恢复点。

工具链校验不会启动代理客户端；实际出口、DNS、视频切组和手机网络切换需分别实测。
